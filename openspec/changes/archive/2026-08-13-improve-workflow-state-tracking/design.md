## Context

See proposal.md - Why. `ClusterRecord` (`src/types.ts`) already splits consent tracking across `consentStatus` (owner-facing decision), `actionOutcome` (reconciliation execution result), and several mechanism fields (`consentCycleStartedAt`, `remindersSent`, `snoozeUntil`, `snoozeJustification`, `snoozeCount`, `consentTierAtDecision`). That split was deliberately introduced by the archived `cluster-status-accuracy` change to stop conflating decision and outcome, and this change keeps it - it only adds the two fields described below and fixes one interaction gap between manual actions and the consent cycle.

The only place a system-generated "why" currently exists is as literal text passed to `supersedeLiveMessage`/`sendConsentDM` (e.g. `notifications.ts`'s `applyAutoTurnOffDecision`, `reconciliation.ts`'s `notifyActionOutcome`) - it reaches Slack and is then gone. `historyFields.ts`'s `describeAuditEntry` reconstructs a best-guess narration from the enum values alone because there's nothing else to read.

## Goals / Non-Goals

**Goals:**
- Persist the system's own explanation for a state change it drove, so it survives past the live Slack message and can be read back later (dashboard, audit log, per-cluster timeline).
- Make "how long has this cluster been in its current consent status" answerable without walking history entries.
- Close the gap where a manual turn-off leaves a pending/snoozed/approved consent cycle dangling against a cluster that's already off.

**Non-Goals:**
- No change to `consentStatus`'s or `actionOutcome`'s enum values, or to the two-axis (decision vs. outcome) split itself.
- No change to reminder/expiry timing math, snooze-cap enforcement, or re-verification logic - only what gets recorded alongside those existing decisions.
- No UI redesign beyond surfacing the two new fields in the existing Workflow detail-panel group and existing history views.

## Decisions

**Two new fields, not a merged "workflow" model.** `consentStatusChangedAt: string | null` (updated on every `consentStatus` transition) and `workflowNote: string | null` (set only when the system itself drives a transition; cleared - or overwritten - on the next transition). Considered folding these into a single generalized `workflowState`/`workflowStateDate`/`workflowStateComment` triplet replacing `consentStatus`/`actionOutcome` outright; rejected because it would re-conflate decision and outcome (the exact thing `cluster-status-accuracy` just fixed) for a rename with no behavioral upside - see proposal.md's "Explicitly out of scope."

**`workflowNote` is written by the same functions that already decide the transition**, not derived after the fact: `applyAutoTurnOffDecision` (notifications.ts) takes the reason text it already passes to `supersedeLiveMessage` and writes it to the record too; `applyActionOutcome` (reconciliation.ts) writes `"the cluster no longer warranted the action..."` for a skip or the caught `CapellaApiError`'s message for a failure. No new "explain this transition" abstraction - each call site already knows its own reason.

**`workflowNote` is a single nullable string, not a history of explanations.** It reflects only the most recent system-driven transition; a later transition overwrites or clears it (cleared on any owner-driven or manual transition, since those don't need an explanation and a stale one from three transitions ago would mislead). Anyone wanting the full history already has the per-cluster timeline; this field is a live "why is it like this right now," not a log.

**`consentStatusChangedAt` is separate from `consentCycleStartedAt`, not a rename of it.** `consentCycleStartedAt` keeps its exact current meaning and every current write site unchanged (it specifically anchors reminder/expiry math to when the *pending* cycle began, including across a snooze resume). `consentStatusChangedAt` is a new, purely observational timestamp updated on every `consentStatus` write, including transitions `consentCycleStartedAt` doesn't touch (entering snoozed, entering approved, expiring). Keeping them separate avoids the risk of subtly breaking expiry timing while chasing a display-only feature.

**Manual turn-off gets the same full reset manual turn-on already performs**, rather than a narrower "only clear if pending" rule. `setClusterPower`'s `off` entry in `POWER_DIRECTIONS` (manualActions.ts) currently sets `resetConsentCycle: false`; this change makes it `true`, identical to `on`. This means a manual turn-off during an *approved-delete* decision also clears that decision, not just a pending/snoozed one - considered leaving an approved-delete decision live so reconciliation still deletes it later, but rejected: the operator's direct action is the more recent, more specific signal, and silently deleting a cluster shortly after an operator manually turned it off (with no fresh consent, and no indication to the operator that a delete is still queued) is a worse surprise than requiring the owner to be asked again if the cluster later drifts back into a notifiable tier.

**New dashboard columns default to hidden, but must still be listed and toggleable in the Columns menu even under an operator's pre-existing (stale) persisted config.** Found, via manual browser verification, that the Columns menu's checkbox list was derived strictly from the persisted `columnOrder` array (`orderedColumnsForPanel`) - a column added after an operator's config was already saved was simply absent from the menu, not just unchecked. Separately, the persisted `columnVisibility` object was applied verbatim, and the table library treats an absent key as visible - so a newly-added column would default to *shown* for anyone with existing persisted state, the opposite of "hidden by default." Fixed by (a) appending any column missing from a stale `columnOrder`/`columnVisibility` (with `DEFAULT_COLUMN_VISIBILITY` merged *under* the persisted object, not replaced by it) so a genuinely-undecided column falls back to the app's own default instead of an implicit "visible." `moveColumn` had the identical gap (silently no-op'd on a column absent from a stale order) and got the same fix.

**Sync's history-append gate now compares against the last *recorded* history entry, not the live `clusters` table row - a bug fix, not a new decision.** `cluster-sync`'s own existing spec already said history is gated against "that cluster's most recently recorded history entry"; the implementation was actually gating against `freshExisting`/`existingById` (the live table), which another writer (a manual action, a Slack decision, the reconciliation loop) can transiently move away from and back between two sync cycles - passing the live-table gate on each individual write even though neither write, once both landed, represented a real change relative to what's already stored. Manually verified against the live dev database: 223 of 283 stored history rows were byte-identical to their immediately-preceding row across every compared field - a real, long-standing defect, not something this change introduced. Fixed by adding `store.ts`'s `getLatestHistoryEntry` and gating against it (falling back to the live-table snapshot only when there's no stored history yet, i.e. a genuinely new cluster).

**`config` and `status` are two independently-tracked fields, not one bundled field.** `historyFields.ts`'s old `config` entry compared/described the *entire* `ClusterConfig` object, including `status` - so a pure operational-status transition (e.g. "Turned Off" → "Turning Off") displayed as a "Configuration" change, alongside a full (unchanged) resource-shape summary. Split into `config` (shape only: cloud provider, region, Couchbase version, node count, node spec) and a new `status` entry. `historyEntriesDiffer`'s aggregate gating behavior is unchanged (status-only changes still trigger a write, just now attributed to the right field) - this only changes labeling/display and which of the two fields shows as differing.

## Risks / Trade-offs

- [Manual turn-off now clears an approved-delete decision too, not just pending/snoozed ones] → Accepted per the decision above; this is a strictly safer default than today's silent gap, and matches the mental model manual turn-on already established.
- [`workflowNote` could theoretically leak a raw Capella error message to the dashboard/audit log that wasn't written with an end-user audience in mind] → Accepted: this is materially better than today, where the same error text only ever reaches server logs; if a specific message proves confusing in practice it's a follow-up wording fix, not a reason to withhold the field.
- [Two similarly-named timestamp fields (`consentCycleStartedAt`, `consentStatusChangedAt`) on the same record could be confused by a future contributor] → Mitigated by keeping the existing field's doc-comment unchanged and adding a doc-comment on the new one that explicitly cross-references the distinction (as already done elsewhere in `types.ts` for related fields).
- [`getLatestHistoryEntry` adds one query per cluster per sync cycle (N+1), on top of the existing per-cluster work already in that loop] → Accepted: matches the existing N+1 pattern `getLifecycleAuditLog` already uses for `getPreviousHistoryEntry`, and cluster counts for this tool are small (tens, not thousands); revisit only if that assumption stops holding.
- [Existing history rows already written under the old live-table gate stay in the store as-is - the fix only prevents *future* no-op rows, it doesn't retroactively clean up the ones already there] → Accepted as out of scope for this change; a one-time cleanup pass (if wanted) is a separate, explicit, and reversible decision the operator should make deliberately, not something to fold into a code change.

## Migration Plan

Additive fields only - existing stored records simply have `consentStatusChangedAt: null` and `workflowNote: null` until their next consent-status or action-outcome transition writes them, the same backward-compatibility pattern already used for other optional `ClusterRecord` fields (e.g. `orgConfigId`, `lastNotifiedAgeStatus`). No backfill, no data migration, no rollback concerns beyond a normal code revert.
