## 8. Fix no-op sync history entries and Configuration/Status conflation

**Discovered from real user feedback on live history data, not part of the original task breakdown.**

- [x] 8.1 Diagnosed a real user report ("we don't need to protocol syncs where nothing has changed") by directly querying the live dev database: 223 of 283 stored history rows were byte-identical to their immediately-preceding row across every field `historyEntriesDiffer`/`computeFieldChanges` compares. Root cause: `sync.ts`'s append gate compared against the live `clusters` table (`freshExisting`/`existingById`), which another writer (manual action, Slack decision, reconciliation) can transiently move away from and back between two sync cycles - each individual write's own gate check can see a "diff" even though, once both land, nothing changed relative to what's actually stored. `cluster-sync`'s own spec already specified gating against "that cluster's most recently recorded history entry" - the implementation had drifted from its own spec; this is a bug fix, not new scope.
- [x] 8.2 Added `getLatestHistoryEntry(clusterId)` to `src/lib/store.ts` (unconditional latest-row lookup, reusing `previousHistoryRow`'s no-cutoff mode).
- [x] 8.3 Changed `sync.ts`'s append gate to use `getLatestHistoryEntry` as `prior`, falling back to the live-table snapshot only when there's no stored history yet (a genuinely new cluster). Verified live: before the fix, a routine refresh wrote one row per cluster regardless of real change; after, only clusters with an actual difference from their last recorded entry got a new row (confirmed via direct sqlite query before/after triggering a refresh through the running dev server).
- [x] 8.4 Diagnosed the second report ("what is Configuration for, if only status changed") - `historyFields.ts`'s `config` entry compared/described the *entire* `ClusterConfig`, bundling resource shape with operational status, so a pure status transition displayed as a full "Configuration" change.
- [x] 8.5 Split `historyFields.ts`'s `config` entry into `config` (shape only - cloud provider, region, Couchbase version, node count, node spec, via a new `configShapeSignature` helper) and a new `status` entry (`a.config.status !== b.config.status`, described via the existing `formatStatusLabel`). Verified live: a pure status transition now shows as "Status: Turning On → Healthy" instead of "Configuration: 1× 2vCPU/8GB, aws/us-east-1, Turned Off → 1× 2vCPU/8GB, aws/us-east-1, Turning Off".
- [x] 8.6 Added spec deltas: `cluster-sync`'s "Cluster record persistence" requirement (MODIFIED, to match what it already said and add the new compared fields to its explicit list, which had drifted out of sync with `HISTORY_FIELDS` even before this change) and `cluster-history-ui`'s new "History tracks operational status separately from configuration" requirement (ADDED).
- [x] 8.7 Ran the full test suite and `tsc` again to confirm no regressions from either fix.

**Not done, by design**: existing history rows already written under the old live-table gate remain in the store - this fix only prevents *future* no-op rows. A retroactive cleanup of the ~223 already-stored no-op rows was deliberately left out (see design.md's Risks/Trade-offs) as a separate, explicit decision for the operator to make.
