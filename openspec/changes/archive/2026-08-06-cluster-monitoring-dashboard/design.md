## Context

See proposal.md for motivation. This is a greenfield project (empty repo) with no existing architecture to integrate with. Key constraints carried over from discovery:

- Scale is small: ~100 clusters maximum across all organizations combined.
- Deployment is a single always-on Node.js process (container or VM), not serverless — this is what makes a flat-file JSON store viable at all (single writer, no ephemeral filesystem, no cross-instance state problem).
- Capella Management API v4: Bearer-token org API keys, 100 requests/min per key, 90s read / 120s write timeouts.
- Per-cluster "owner" and "last activity" are not native API fields; they must be derived (see Decisions).
- Per-cluster actual cost comes from the Billing API and lags up to ~5 days; it is not real-time.

## Goals / Non-Goals

**Goals:**
- Single background process that syncs cluster state from all configured Capella orgs into one local JSON store.
- One unified, filterable, sortable table UI across all orgs/projects.
- Correct handling of clusters that are temporary and get deleted (tombstone + 7-day retention).
- Resolve the Activity Log API-reachability unknown before it silently becomes a broken "last activity" column.

**Non-Goals:**
- Any cleanup/governance action (pause, delete, notify) — deferred to a future change.
- Rule engine, flags, exemptions, snooze — deferred to a future change.
- Multi-user attribution of actions or an action audit trail — not needed since no actions exist yet.
- High-availability or horizontal scaling of the sync process — scale (~100 clusters) does not warrant it.

## Decisions

### Local JSON store as a single flat collection, not per-org partitions
A single JSON collection (e.g. one `clusters.json`-equivalent structure) with each record tagged by `orgId`/`projectId` lets the dashboard's unified table filter/sort across all orgs without fan-out/merge logic at read time. Per-org partitioned files were considered and rejected because they'd push merge logic into every read path for no benefit at this scale (~100 records total fits comfortably in memory).

### Snapshot history stored separately from current state
Each cluster has a "current record" (latest known state) and an append-only history of snapshots taken on sync. This separation keeps the common read path (render the table) cheap — it only reads current records — while still supporting trend/age/cost-over-time data from history when needed. History entries are pruned per the retention policy independent of the current record.

### Tombstone-then-purge lifecycle for deleted clusters
When a cluster stops appearing in the Capella API, it is marked `deleted` with a timestamp rather than removed immediately. This matches the reality that many monitored clusters are intentionally temporary — operators still want to see "this existed until recently" for a window after teardown. Default retention is 7 days (configurable), after which both the tombstoned record and its history are purged. Rejected alternative: deleting immediately on disappearance — this would make the dashboard blind to very-short-lived clusters that happen to be torn down between two poll cycles landing near a page load.

### Owner derived from creation-event initiating user, with manual override stored locally
Capella has no `owner` field. The creation event's initiating user is the best available proxy, but clusters outlive the people who created them, so the local store must support a manual override that takes precedence over the derived value on every subsequent sync. The override lives in the same local record, not a separate table, since it's a property of the cluster from the dashboard's perspective.

### Estimated cost (live) shown alongside actual cost (lagging), not merged into one figure
Estimated cost (node spec × published credit rate × uptime) is computed fresh every sync cycle and is always current. Actual cost from the Billing API can lag up to 5 days. These are kept as two distinct columns rather than reconciled into one, so a large discrepancy between them (e.g. from data-transfer or backup charges the estimate doesn't model) stays visible instead of being silently averaged away.

### Activity Log reachability is an unresolved risk requiring a spike, not an assumption
Discovery could not confirm whether Capella's Activity Log (org/project/cluster event stream with initiating user, timestamp, severity) is exposed through the public Management API or is console-only. This directly affects the "last activity" requirement (and is a secondary corroborating signal for owner). Rather than build the sync process assuming API access exists, the first implementation task must spike this specifically: attempt to retrieve Activity Log data via the Management API with a real org API key, and confirm or rule it out. The cluster-sync spec already defines both paths (API-sourced vs. sync-observed fallback) so no spec change is needed regardless of the spike's outcome — only the sync implementation branches on the result.

### Login/session auth with a single shared credential for this phase
A real login form + session cookie (not HTTP Basic) is required, backed by a small local credential store. Since no destructive actions exist in this phase, a single shared login is sufficient; per-user accounts and action attribution are deferred to the future governance change, where they'll actually matter.

### Org name, owner, and a better last-activity fallback all come from data already being fetched
Comparing against a real Capella console screenshot during testing surfaced that the cluster resource's `audit` block (confirmed in Couchbase's own docs to include `createdAt`, `createdBy`, `modifiedAt`, `modifiedBy`) was already being fetched on every sync but only `createdAt` was used - `createdBy` sat unused despite it being exactly what the console's own "Created by" column derives from. Three fixes followed from this:
- **Org name**: fetched fresh from `GET /organizations/{orgId}` every cycle instead of requiring the user to type it in `CAPELLA_ORGS`; the config field is now an optional fallback label only.
- **Owner**: now derived from `audit.createdBy` (a user ID) resolved to a display name via the Users API, cached per sync cycle. This replaces the earlier Activity-Log-only approach, which required an unconfirmed endpoint and only produced a name if a matching "creation" event happened to be found in the log.
- **Last activity fallback**: when the Activity Log isn't reachable, `audit.modifiedAt` - a real, confirmed, always-available field - is now used ahead of the old sync-observed fingerprint-diffing, which could only be as fresh as our own poll interval and depended on us having already seen a prior snapshot.
The Activity Log is still tried first when reachable, since it can reflect actual query/data activity rather than just configuration changes - `audit.modifiedAt` is a better-grounded approximation, not a full replacement.

Known remaining gaps identified from the same screenshot comparison, not yet implemented because the exact API field names/shapes weren't confirmed: single-AZ vs. multi-AZ, and support plan tier. `couchbaseVersion` is already fetched but not yet surfaced in the UI.

Cluster operational state (running vs. turned off) was subsequently implemented: `ClusterConfig.status` reads `currentState`/`status` defensively off the raw API response (the exact field name wasn't confirmed in docs beforehand). A real sync against a live account later confirmed the value is literally `"turnedOff"`, validating the defensive implementation and the "off"-substring-based badge styling in the UI.

### Single global search instead of per-column filters
Per-column filter inputs (one text box under each header) were replaced with a single search field outside the table that matches against every column's value. Simpler to use for a ~100-row table, and removes a full header row from the table entirely, which also helps the no-horizontal-scroll layout below.

### No horizontal scroll; fixed-width wrapping columns
With 11 columns and no per-column filter row, the table uses `table-layout: fixed` with explicit percentage widths per column (colgroup) and wrapping cell content, instead of `overflow-x-auto` with `whitespace-nowrap`. Trade-off: rows are taller (owner emails and cost-with-date strings wrap onto 2+ lines) instead of the table scrolling sideways - accepted since a horizontal scrollbar on the primary view was explicitly unwanted.

### TanStack Table for sort/search, still headless
The hand-rolled sort/global-search logic was replaced with `@tanstack/react-table` (v8.21.3, not the v9 that had just gone stable at the time - v9's breaking API changes were too fresh to implement with confidence). It's a headless library: no bundled markup or CSS, so the existing Tailwind table structure, `table-fixed` layout, and column width percentages (carried via each column's `meta.widthPct`) didn't need to change. Chosen over a batteries-included grid (AG Grid, MUI DataGrid) because those ship their own styling/theming that would have fought the existing design rather than slotting into it.

### TanStack feature set: grouping, column customization, pagination, row expansion
Grouping (by org/project/owner, with summed cost aggregation), column visibility/ordering, row detail expansion, and pagination were all added on top of the same headless table. Column pinning and resizing were tried and then deliberately dropped: pinning had no scroll to freeze against (the table intentionally has none) and only ever provided cosmetic edge-anchoring, and resizing wasn't needed given a fixed 12-column layout - both added real implementation complexity (proportional-resize math, sticky-position bookkeeping) for marginal value, so removing them was a straightforward simplification once asked for.

- **Row expansion is two separate mechanisms, not one.** TanStack's `expanded` state is used only for group-row expand/collapse (the natural pairing with grouping's sub-rows). A per-cluster "view details" toggle (showing cluster/org/project IDs, Couchbase version, storage spec) uses a separate local `Set<string>` of open row IDs, rendered as an extra `<tr>` - conflating the two would have meant a leaf row's "show details" fighting with TanStack's grouping-oriented expand semantics.
- **Hiding a column must not hide its data.** The detail-expansion panel also lists the value of every currently-hidden column (via a small `columnId -> {label, value}` lookup against the row's already-computed display fields), so toggling a column off in the Columns panel narrows the table without making that data unreachable.
- **Configuration persists via localStorage**, not a server-side store: column visibility, column order, sort state, and page-size preference are written to `localStorage` on change and restored on mount. Deliberately excluded from persistence: the search term and current page index (so a returning user doesn't land on a confusing filtered/mid-pagination view), and grouping/row-expansion state (transient view state, not "configuration"). Reading `localStorage` during render would break server/client hydration (the server has no localStorage), so restoration happens in a `useEffect` after mount, gated by a `configLoaded` flag that also prevents the save-effect from clobbering the not-yet-loaded persisted config with the initial defaults.

**Gotcha #1**: seeding initial `columnOrder` state from `columns.map(c => c.id)` (reading `.id` off the raw pre-table column definitions) silently produced `undefined` for every column created via `columnHelper.accessor("someKey", {...})` without an explicit `id:` override - that property isn't resolved until the definitions are processed by the table. Fixed by starting `columnOrder` as `[]` (TanStack already treats empty as "use natural definition order") and only ever reading a real, resolved column-id list from `table.getAllLeafColumns()` when a move action actually needs one.

**Gotcha #2**: after adding pagination, the dashboard threw "Can't perform a React state update on a component that hasn't mounted yet" on every login. Traced via a monkey-patched `console.error` capturing a real JS stack (guessing at TanStack side effects from the error text alone was a dead end): the cause was `autoResetPageIndex` (default `true`) - TanStack resets the page index as a side effect of computing the row model whenever the filtered set changes, and on the very first render that reset fires before the component has finished mounting. Fixed by setting `autoResetPageIndex: false` and instead resetting `pageIndex` to 0 explicitly in a `useEffect` keyed on `globalFilter` - functionally identical (search still returns you to page 1), but safe because effects run after mount.

### Responsive width and the practical floor of a 12-column table
The 90%-width sizing lives on `<main>` in `app/page.tsx` (`w-full sm:w-[90%] mx-auto`, full width below the 640px `sm` breakpoint), not inside `ClusterTable`. It was tried inside `ClusterTable` first and looked wrong - `<main>` still carried a leftover `max-w-[1400px]` cap from before this feature existed, so the table's 90% was being computed against an already-capped 1352px content box rather than the real viewport; past ~1500px of actual browser width the table's absolute size stopped growing at all, so on a wide monitor it visibly looked like far less than 90%. Fixed by moving the 90% sizing to `<main>` itself (dropping the `max-w-[1400px]` cap it replaces) so the header and the table share the exact same width consistently, and by removing the now-redundant width class from `ClusterTable`'s own wrapper - stacking two independent 90%-of-parent widths would have compounded to ~81%, a different wrong number. Verified directly: at a 2400px viewport, `<main>` measures exactly 90.0% with symmetric 120px margins on each side, and the header and table box widths match to within a couple of pixels (border-width rounding).

Measured directly rather than assumed: no horizontal scrollbar appears from 640px up through at least 2400px. Below 500px, one reappears - twelve columns cannot fit meaningfully in that space even with wrapping, and forcing it further would mean either auto-hiding columns by default on small screens (a real feature, not attempted here) or shrinking text below a legible size. Between those extremes (roughly 640-1024px), initial testing showed only the *first* threshold held: wrapping degraded to breaking individual words character-by-character (e.g. "days" as "d/a/y/s" on separate lines) because the reduced-padding/font-size styles were gated behind the `md` breakpoint (768px) while the character-shattering was actually observed at 900px, above it. Moving the compact styles to the `lg` breakpoint (1024px) fixed this - the lesson, twice over in this section, being to measure the actual rendered pixels rather than assume a Tailwind breakpoint choice is doing what it sounds like it should.

### The dashboard page must be forced dynamic
Discovered when testing with `next start`: `app/page.tsx` reads the local JSON store directly via `fs`, not through `fetch()`, so Next.js has no signal that the page depends on runtime state and was statically pre-rendering it at build time - freezing the dashboard on whatever the store contained during `next build` and never re-reading it per request. Invisible under `next dev` (which always renders fresh), only surfaced under a production-style build. Fixed with `export const dynamic = "force-dynamic"` in `app/page.tsx`. Worth remembering for any future page that reads the store directly.

### Owner override removed; date/time formatting moved to the client
Two changes made together because the second one changes where data has to live for the first one's cleanup to be complete.

**Owner editing removed.** The inline "edit" control on the owner cell was removed per explicit request. Since it was the only thing that ever called `updateOwnerAction`, which was the only caller of `setOwnerOverride`, both were deleted rather than left as unreachable code - along with the `ownerOverride` field itself (`ClusterRecord`, `sync.ts`, `page.tsx`'s owner fallback), since a persisted-but-unsettable override is a half-feature, not a harmless no-op. The cluster-sync spec's "Owner derivation" requirement was trimmed to match: derivation only, no manual override. If per-cluster owner correction is wanted again later, it should come back as a deliberate feature (who can set it, is it audited, etc.), not by resurrecting this path.

**Date/time formatting moved from server to client.** All date/time display (`createdAtLabel`, `lastActivityLabel`, the cost-as-of date, last-synced) used to be pre-formatted in `app/page.tsx` - a Server Component - via `.toLocaleString()` with no explicit locale. That call was always resolving against *the Node server's* locale, never the visiting browser's, so "respect the browser's region settings" was impossible to satisfy from there regardless of formatting options. Fixed by passing raw timestamps (`createdAtMs`, `lastActivityMs: number | null`, `actualCostAsOfMs`, `lastSyncedAtMs`) down to `ClusterTable` (a Client Component) and formatting them there with `toLocaleString(undefined, { year: "2-digit", month: "numeric", day: "numeric", hour: "numeric", minute: "numeric" })` - `undefined` locale means "the runtime's own default," which is the actual browser once code runs client-side. Omitting `second` from the options is what drops seconds; not setting `hour12` is what lets 12h/24h follow the locale instead of being forced.

**First attempt was wrong, and shipped anyway.** A Client Component's first render also happens on the server (for the initial HTML), where `toLocaleString(undefined, ...)` resolves to the Node server's locale, not the browser's. The first fix reached for `suppressHydrationWarning` - React's own docs use this exact "locale-dependent date string" scenario as their canonical example, so it looked like the sanctioned answer. It compiled, and a same-process Playwright check with a spoofed browser locale even appeared to confirm it, because that test's assertions ran after enough incidental re-renders (sorting, etc.) to mask the actual defect. The real behavior: `suppressHydrationWarning` only tells React not to *warn* about the server/client text mismatch during the one-time hydration diff - it does not schedule a re-render to correct that mismatch afterward. With nothing else to trigger one, the dates stayed frozen at whatever the *server's* locale produced, permanently, for any user whose browser locale actually differed from the server's. A real user in Germany reported still seeing US-formatted dates, which is exactly this: the deployment server's locale, not theirs.

**Actual fix**: a `FormattedDateTime` component renders a neutral, locale-independent placeholder (`…`) for both the server render and the first client paint - identical output, so there is no mismatch to suppress in the first place - then swaps to the real `toLocaleString(undefined, ...)` value once mounted, via a genuine `useEffect`-triggered state update. That's a normal post-hydration re-render, not a hydration correction, so React actually applies it. Verified this time by fetching the raw server-rendered HTML directly (`curl` with an extracted session cookie, bypassing the browser entirely) and confirming the date cells contain literal `…` before any client JS has run - not a plausible-looking assertion, the actual markup. Re-verified end-to-end under simulated `de-DE` and `en-GB` browser locales afterward: correct locale-specific formatting, zero console errors.

The lesson: a fix that merely stops React from *complaining* about wrong output is not the same as a fix that produces *correct* output - and a test that passes because of incidental re-renders elsewhere in the flow doesn't prove the mechanism you think it proves. Checking the actual server-sent bytes would have caught this the first time.

**Confirmed not a bug**: a user reported still seeing `31/07/26, 16:03` (slashes, leading zeros) rather than the German `31.7.26` (dots) they expected, despite the fix working. `navigator.language` in their browser turned out to be `en-GB`, not `de-DE` - a browser/OS language preference, unrelated to the physical machine's location and entirely outside the Node server's involvement (this is the client-side fix from above; the server was never in this loop). Physical location and configured browser locale are independent; the code is correctly respecting whichever locale the browser actually reports, and hardcoding a "region" from IP/host geography to override an explicit browser preference would be the actual bug.

### Estimated cost column removed entirely
The "Est. Cost/mo" column (node spec × placeholder credit rate × uptime, `src/pricing.ts` + `src/lib/costEstimate.ts`) was removed per explicit request after a user compared it against a real cluster and asked where the number came from. The rates in `src/pricing.ts` were never real - the file's own comment said so - and Couchbase doesn't publish a single per-unit rate table (it depends on cloud provider, region, and commitment tier), so there was no way to make the column trustworthy without the user's actual Capella pricing agreement, which wasn't available. Rather than leave a column that looks authoritative but isn't, both files were deleted along with the `estimatedCostPerMonthUsd` field (`ClusterRecord`, `sync.ts`, `page.tsx`, `ClusterTable.tsx`) - a placeholder number nobody can act on is worse than no number. The cluster-sync and cluster-dashboard-ui specs' cost requirements were trimmed to match: actual cost only. If a real estimate is wanted later, it should come back with real per-provider/region/tier rates, not placeholders.

### "approx." indicator removed
The badge marking a last-activity value as approximate (shown when it came from the sync process's own change-detection fallback rather than the Activity Log) was removed from the table per explicit request, along with the now-unused `lastActivityApprox` field on `ClusterRow`/in `app/page.tsx`'s row mapping. The underlying data-model distinction this was surfacing - `ClusterRecord.lastActivitySource`, and the Activity-Log-vs-sync-observed branching in `sync.ts` - was left intact; it's real provenance information the sync process still needs internally and the cluster-sync spec still requires, independent of whether the dashboard displays a badge for it. Only the UI-facing scenario in the cluster-dashboard-ui spec was removed.

## Risks / Trade-offs

- **[Risk]** Activity Log may not be reachable via the Management API → **Mitigation**: implemented as a runtime probe, not a build-time assumption - `getActivityLog` attempts a candidate endpoint and `sync.ts` treats any failure as "not reachable," falling back to sync-observed activity automatically. The live spike (task 2.4) confirming the exact endpoint path against a real org API key is still outstanding - no Capella credentials were available in the environment that implemented this change. The UI and store schema do not need to change regardless of that spike's outcome.
- **[Risk, resolved by removal]** Estimated cost model (node spec × published rate × uptime) would not match actual billed cost exactly (data transfer, backup, support tier surcharges aren't modeled) → the mitigation (two distinct columns, so the gap stays visible) turned out to be insufficient once a user compared the number against a real cluster and found it had no relation to real pricing - see "Estimated cost column removed entirely" above. The column no longer exists.
- **[Risk]** Single-process, single-writer JSON file store has no built-in corruption recovery if the process is killed mid-write → **Mitigation**: acceptable at this scale/criticality (a monitoring dashboard, not a system of record for billing); write-then-rename (atomic replace) avoids partial-file corruption on crash.
- **[Trade-off]** No horizontal scaling or serverless deployment is possible with this design → accepted, since deployment topology is already fixed to a single always-on process and scale is capped at ~100 clusters.

## Migration Plan

Not applicable — greenfield project, no existing system to migrate from or roll back to. Initial deployment is: configure org API keys and credential store, start the process, let the first sync cycle populate the store, dashboard becomes usable once the first sync completes.

## Full API conformance audit against the official spec

Every prior endpoint fix in this project was reactive: something broke, a docs page got fetched, a best guess got shipped. Asked to instead verify the *entire* client against the authoritative source in one pass, rather than one broken thing at a time.

**Finding the real spec.** The official reference (`docs.couchbase.com/cloud/management-api-reference/index.html`) is a large single-page app; fetching it (even with a URL fragment naming a specific operation) kept returning different, incomplete slices of the same document, because fragments are client-side-only and never reach the server - every fetch requested the identical full page, and different amounts of it made it into a summary each time. That's a structural limitation, not a fluke, and it's why earlier fixes based on fetching this page were sometimes wrong. Inspecting the page's raw HTML directly (`curl`, not a summarizing fetch) surfaced the actual OpenAPI source it renders from: `_attachments/openapi.external.generated.yaml`, a plain 26,000-line YAML file. Downloaded and grepped directly - no AI summarization step, no lossy sampling - which is what made this audit reliable where prior attempts weren't.

**Confirmed already correct**: `getOrganization` (`GET /organizations/{orgId}`), `getUser` (`GET /organizations/{orgId}/users/{userId}`), `listProjects` (`GET /organizations/{orgId}/projects`), `listClusters` (`GET /organizations/{orgId}/projects/{projectId}/clusters`), and every field `toClusterConfig` reads (`cloudProvider.type/region`, `couchbaseServer.version`, `serviceGroups[].node.compute.cpu/ram`, `serviceGroups[].node.disk.type/storage/iops`, `numOfNodes`, `audit.{createdAt,createdBy,modifiedAt,modifiedBy}`, and `currentState` - confirmed required and enumerated, including the literal value `"turnedOff"` this app already depends on). None of these changed.

**Confirmed wrong and fixed - Activity Log.** `getActivityLog` called a cluster-scoped path, `.../clusters/{clusterId}/events`, that does not exist anywhere in the spec. The real endpoint is org-scoped: `GET /organizations/{orgId}/events`, filtered to one cluster via a `clusterIds` query parameter, with `sortBy=timestamp&sortDirection=desc&perPage=1` doing the "give me the single most recent event" work server-side instead of client-side sorting. One correction to the constraints, easy to miss: `from` defaults to *the last 24 hours* if omitted - not "all history" - so it's now pinned to a fixed early date to cover a cluster's full lifetime instead of silently only ever seeing same-day activity.

**Confirmed wrong and fixed - Billing.** `getBillingUsage` called `GET /organizations/{orgId}/billing/usage?clusterId=...` - also nonexistent, and the wrong HTTP method besides. The real endpoint, `POST /organizations/{orgId}/projects/{projectId}/clusters/{clusterId}/billing` ("Get Itemized Billing Per Cluster"), needs the project ID (the function signature gained one), a JSON body (`startDate`/`endDate`, `YYYY-MM-DD`), and reads `data.total.totalCurrencySpend` from the response rather than a top-level array. Query range is the current calendar month to date. One real limitation surfaced by the schema itself: an org billed in credits rather than currency gets `totalCurrencySpend: null` (only `totalCreditSpend` populated) - converting that to USD would need a real published rate, which per `src/pricing.ts` doesn't exist, so this returns "no actual cost data" rather than guess one. This was the root cause of "Actual Cost" showing empty for every cluster the whole time - not a lag, a call that never succeeded.

**Known limitation, not fixed**: `listProjects`/`listClusters` responses include a `cursor` field for pagination (confirmed via `GetProjectsResponse`/`GetClustersResponse`) that the client doesn't follow - only the first page is read. Not touched here since it's a real gap but a low-risk one at the project's own stated scale (~100 clusters total); worth revisiting if any org's project or cluster count turns out to exceed one page.

**Not independently verified end-to-end**: this audit confirms every path/method/schema against the *official spec*, which is a materially stronger basis than the prior guesses - but none of it has been re-run against a real Capella account from this environment (no credentials here). The next real sync (via the Refresh button) against the user's actual account is the remaining verification step.
