## Context

`app/components/DashboardTabs.tsx` is a client component that owns `useState<Tab>("clusters" | "history")` and renders a `role="tablist"` segmented control above whichever table (`ClusterTable` or `HistoryTable`) is active. It's mounted once, in `app/page.tsx`, inside `<main className="mx-auto w-full px-6 py-8 sm:w-[90%]">`, below a header row (wordmark, Slack indicator, `ThemeToggle`, Settings link, `RefreshButton`, logout form).

A Stitch-generated mock (recorded in `DESIGN.md`, "Sidebar exploration") explores a left sidebar in place of that tab bar: `w-64`, `canvas` background, `line` right border, an active item on `brand-soft`/`brand`, inactive items in `ink-muted`. It was generated as a full standalone page (its own header/body), not embedded in this app's existing chrome, and it hides the sidebar below the `md` breakpoint with no fallback. It also uses Google's Material Symbols web font for icons, which conflicts with this codebase's zero-icon-font-dependency convention (see `capella-branded-theme` design.md, Decision 7 / hand-rolled SVGs used everywhere else).

See proposal.md for why (pure navigation-affordance change, no spec-level behavior change).

## Goals / Non-Goals

**Goals:**
- Replace the tab bar with a left sidebar nav, visually matching the mock's color/spacing/active-state rules.
- Preserve every existing behavior: which views exist (Clusters, History), their content, the row-count badges, and keyboard/AT semantics for switching between them.
- Zero new dependencies (no icon font, no nav library).

**Non-Goals:**
- Adopting the mock's page chrome (its own header, "Global Fleet" sidebar heading) - this app's existing header stays as-is.
- Adding the mock's "Templates"/"Analytics" nav items - not real features (proposal.md).
- Any change to the header, Settings page, or table internals.

## Decisions

**1. Sidebar is full-bleed to the viewport edge, full height; the page no longer centers at 90% width. (Revised after first implementation pass.)**
The first pass embedded the sidebar inside the existing `mx-auto ... sm:w-[90%]` centered container, boxed with its own border/rounded corners/background - to limit blast radius (see original alternative below, then rejected in review). Reviewing the live result against the mock showed this reads as a small inset "side panel" rather than a real sidebar, and wastes the margin outside the 90% container on wide screens - not what the mock communicates. Revised approach: `app/page.tsx`'s outer wrapper becomes a full-height `flex flex-col`; the header spans the full viewport width (its own `px-6 py-4` + bottom border replaces the old page-level `px-6 py-8`); a `flex flex-1` row below it holds the sidebar (`<aside>`, full height via flex stretch, `border-r`, no rounded box) and the content pane. The `cluster-dashboard-ui` "table is 90% of its available container width" requirement still holds - it's just re-scoped to the content pane (viewport width minus the sidebar) instead of the whole page, via a `mx-auto sm:w-[90%]` wrapper *inside* the content pane around the table only, not around the sidebar+content pane as a whole.
- *Original alternative (first pass, since rejected)*: sidebar embedded inside the existing centered container, boxed with a border and rounded corners. Rejected after visual review - reads as a "side panel," not a sidebar, and leaves the outer 10% margin unused on wide screens.
- *Alternative considered here*: also drop the table's 90%-of-container rule and let it go full-width in the content pane, matching the mock pixel-for-pixel. Rejected at the time without deliberate scope expansion - that rule is an existing `cluster-dashboard-ui` requirement, not something a navigation-only change should touch unprompted. **Superseded by Decision 6**: the user explicitly asked for the table to use more of the content pane, which does warrant the requirement change.

**2. Sidebar stays visible at every viewport width - the mock's `hidden md:flex` breakpoint is not carried over.**
The mock hides the sidebar below `md` (768px) with no replacement, which would silently remove the only way to reach the History view on narrower screens. The existing table spec already commits to usability down to 640px (`cluster-dashboard-ui` - "No horizontal scrolling; cell content wraps" / "Table width matches its container proportionally"), so regressing navigation itself below that width isn't acceptable.
- *Alternative considered*: collapse to an icon-only rail below `md`. Rejected as unnecessary complexity for an internal ops tool that's desktop-first in practice; always-visible full sidebar is simpler and matches today's tab bar, which has no responsive hide behavior either.

**3. Icons are hand-rolled inline SVGs, not the mock's Material Symbols web font.**
Matches the existing codebase convention (zero net UI/icon-library dependencies; see `capella-branded-theme` design.md). Two simple icons are needed (a stacked-database glyph for Clusters, a clock/history glyph for History) - small enough to inline directly in `DashboardTabs.tsx`, consistent with how other components (e.g. `ManualDeleteButton.tsx`) inline their own SVGs rather than sharing an icon set.
- *Alternative considered*: pull in an icon package (e.g. lucide-react). Rejected - proposal explicitly commits to no new dependencies, and the project has zero net UI dependencies today.

**4. `DashboardTabs.tsx` keeps its file name and exported `Tab` type/props, even though it no longer renders literal tabs.**
Renaming would touch its one import site (`app/page.tsx`) for no functional benefit and adds unrelated diff noise to a navigation-affordance change. The component's responsibility (own view-switch state, render the active table) is unchanged - only its nav markup changes internally.
- *Alternative considered*: rename to e.g. `DashboardNav.tsx` for accuracy. Rejected as churn disproportionate to the change; can be revisited if a future change gives it more reason to move.

**5. Row-count badges move from inline next to the label (tab bar) to the same position within each sidebar nav item.**
No behavior change - same counts, same source (`clusterRows.length` / `historyRows.length`), just repositioned to fit a vertical nav item instead of a horizontal tab.

**6. Sidebar narrows to `w-52` (208px, from `w-64`/256px); the table drops the 90%-of-container inset entirely and fills its content-pane container. (Second revision, direct user feedback.)**
After seeing the full-bleed sidebar (Decision 1) live, the user asked for the sidebar to be narrower and for the table to use more of the main section - i.e. the 90%-of-container inset (kept, re-scoped, in Decision 1) still left visible unused margin now that the content pane itself already has padding providing edge breathing room. This is a genuine change to the `cluster-dashboard-ui` "Table width matches its container proportionally" requirement (not just an implementation detail), so it's captured as a `MODIFIED` delta in this change's `specs/cluster-dashboard-ui/spec.md`: the table now always fills its container's full width, with edge spacing coming from the container's own padding instead of a proportional inset. `w-52` for the sidebar was chosen as a noticeably narrower width that still comfortably fits both nav items' icon + label + count at their current padding (checked against "History", the longer label).
- *Alternative considered*: keep the 90% inset but reduce the content pane's own `p-6` padding to make the combined unused space smaller. Rejected - doesn't address the actual ask (table should use *more* space, not just have less padding around a still-90%-wide table), and produces a less clean, two-source-of-spacing result.

**7. Sidebar is user-collapsible (icon-only when collapsed), state persisted in `localStorage`; the toggle lives at the top of the sidebar, not the bottom. (Third revision, direct user feedback.)**
A manual collapse toggle (chevron button) shrinks the sidebar from `w-52` to `w-16`, hiding each nav item's label and count and centering just its icon; the label remains available via a native `title` tooltip on the button, so it's still discoverable without a custom tooltip component. This is a user-triggered choice, not a responsive/viewport-driven one, so it doesn't reopen Decision 2 (which rejected *automatically* hiding the sidebar below a breakpoint, since that would silently remove the only way to reach History) - a manually-collapsed sidebar still shows both nav icons and both remain one click away at every viewport width. Collapsed/expanded state persists in `localStorage` under `capella-housekeeper:sidebar-collapsed:v1`, read/written with the same mounted-gate `useEffect` pattern `ClusterTable.tsx` already uses for its own persisted table config (`capella-housekeeper:table-config:v1`) - reading `localStorage` during render would break server/client hydration since the server has no `localStorage`. The first implementation copied only half of that pattern (the load effect) and omitted `ClusterTable`'s `configLoaded` guard on the save effect; without it, the save effect fires on mount with the pre-load `false` default and clobbers whatever the load effect just read, so a reload always landed back on expanded. Adding the equivalent `collapsedLoaded` guard (save effect no-ops until the load effect has run once) fixed it - caught by the reload step of the Playwright verification below, not by code review.
- *Alternative considered, then reverted*: pin the toggle to the bottom of the sidebar via `mt-auto`. First implementation did this; live verification found it overlapping Next.js's own dev-mode floating indicator badge (bottom-left corner) closely enough that Playwright's click on the resulting "Expand sidebar" button timed out (covered by the other element). That's a dev-only artifact (the indicator doesn't exist in production), but the bottom-left corner is a common landing spot for injected browser/devtool/widget UI in general, so the toggle moved to the top of the sidebar instead - also a more conventional placement for a sidebar collapse control.
- *Alternative considered*: no persistence (always start expanded). Rejected - inconsistent with this codebase's existing convention of persisting user display preferences (table column visibility/order/sort/page-size, theme) across reloads.
- *Alternative considered*: a custom tooltip component for collapsed labels. Rejected - a native `title` attribute needs no new component or dependency and is sufficient for a two-item nav.

**8. A second Stitch mock ("Dashboard: High-Density Ops View") is adopted selectively, not wholesale - see proposal.md for the user's explicit scoping choices.**
That mock includes: a hover-to-expand icon sidebar with extra nav items (Organizations/Owners/Reports) that don't exist as features; KPI stat tiles for Total Clusters, Active Nodes, CPU Usage, and Memory; a "Cluster Performance" weekly bar chart; a denser table card style; a per-row-contextual Action column (varies by status - single Delete for healthy rows, Power+Delete for stale, a full-width "Delete Now" for forgotten, Power-on for turned-off, a spinner for pending) with no Consent column at all. The user selected only: header/toolbar/table visual density, a Total-Clusters stat tile, and a chart - explicitly declining the hover-sidebar/extra-nav-items and the Action-column/Consent-column redesign (the latter would have conflicted with the existing `cluster-dashboard-ui` "Unified action column" requirement, same category of conflict as Decision 6's table-width change, but this time the user didn't ask for the requirement itself to change).
- Of the three selected items, two needed a data-honesty adjustment rather than a literal port:
  - **Total Clusters**: real data (`clusterRows.length`), already computed - a direct, faithful port.
  - **Active Nodes / CPU Usage / Memory tiles**: dropped entirely (not selected) - this app has no node count, CPU, or memory metrics from Capella, and fabricating plausible-looking numbers in an ops tool that's specifically for tracking real cluster state would be actively misleading.
  - **"Cluster Performance" chart**: the mock's bars are a fake CPU/utilization percentage time series (hardcoded per-day heights, no such metric exists in this app). Substituted with a **"Weekly Activity" chart** - the same visual shape (7 bars, day labels) but showing a genuine, already-available number: count of lifecycle audit-log entries per day for the rolling last 7 days (from the same data `HistoryTable` renders). Y-axis is not labeled as a percentage (there's no 0-100% scale for a count); bars are scaled relative to the week's own max count, with the count shown above each bar. Day boundaries and weekday labels are computed **client-side in `DashboardTabs.tsx`, gated behind a mounted `useEffect`** rather than server-side in `page.tsx` - which local calendar day a timestamp falls into, and what to call that day, both depend on the visitor's own timezone/locale, which a server component can't know. This is the same reasoning (and the same mounted-gate mechanism) this codebase already applies to `FormattedDateTime` and `ThemeToggle`'s system-preference resolution; computing it server-side would silently use the server's timezone instead and could bucket events into the wrong day for a visitor elsewhere.
- *Alternative considered*: ask the user to defer the chart/KPI items until real Capella metrics integration exists. Not needed - the user's own selection ("Total Clusters only") already excluded the metrics that would've required that, and the chart has a genuine substitute in already-collected data.

**9. Settings, theme toggle, and Slack connection status move from the page header into the sidebar footer, with a collapsed-icon variant; Refresh moves next to the Columns button inside `ClusterTable`. (Direct user follow-up request.)**
After reviewing the ops-view mock's minimal header (title + search only), the user asked to relocate the header's secondary controls into the sidebar and reposition Refresh. The header now holds only the title and the logout control - Settings, Theme, and Slack status render in a `mt-auto` footer block within the sidebar `<aside>` (below the two nav items), matching the mock's own "Bottom Actions" pattern but keeping this app's real controls instead of the mock's placeholder settings/theme icons:
  - **Settings**: a new `SlidersIcon` (three horizontal lines with a knob each - a common settings glyph, easy to hand-draw consistently with this file's existing stroke-icon style) wraps the existing `/settings` `Link`, styled like `NavItem` but without `role="tab"`/`aria-selected` (it's real navigation, not a same-page view switch).
  - **Theme**: `ThemeToggle` gains a `collapsed` prop. Expanded: unchanged 3-button Light/Dark/System control. Collapsed: a single icon button showing the *current* mode's icon (new `SunIcon`/`MoonIcon`/`MonitorIcon`) that cycles Light → Dark → System → Light on click - the existing 3-way state and cookie persistence are unchanged, only the collapsed rendering is new.
  - **Slack status**: `SlackConnectionIndicator` gains a `collapsed` prop. Expanded: unchanged bordered badge. Collapsed: just the colored status dot in an icon-sized slot, with the existing `title` (status detail) as the only way to read status text; the Reconnect button (shown today when disconnected) is only available expanded - collapsed-and-disconnected still shows the dot (rose/red), so the problem is visible, just not actionable without expanding.
  - **Refresh**: `RefreshButton` moves from the header into `ClusterTable.tsx`'s own toolbar, immediately after the Columns button. It no longer appears on the History view - a real trade-off (see Risks) accepted per explicit instruction ("place refresh button to the right from columns button").
- *Alternative considered*: keep a single always-expanded row of icons for Settings/Theme/Slack regardless of sidebar collapse state (skip building collapsed variants for them). Rejected - inconsistent with the two nav items directly above them, which do collapse; a sidebar that only partially collapses reads as broken, not intentional.

**10. Branding moves into the sidebar's top block; the page header becomes a per-view page title. The global full-width header is removed and `app/page.tsx` becomes a thin data-loading shell. (Fourth revision, direct user feedback with zoomed reference screenshots.)**
The user pointed at the ops-view mock's top-left corner specifically: an orange rounded-square brand mark (broom glyph) that sits alone when the rail is narrow and gains a "Housekeeper" wordmark when wide, with a divider under it - and a main-content header showing a *page* title ("Cluster Management"), not the app name. Adopting this inverts the current arrangement (app name in a full-width header above everything, no page title anywhere):
  - The sidebar gains a brand block at its top (`border-b`): a `bg-brand` rounded square holding a hand-drawn broom `BroomIcon` in `brand-ink`, plus a `text-brand` "Housekeeper" wordmark when expanded.
  - The wordmark is "Housekeeper", not "Capella Housekeeper" - at `w-52` the sidebar has ~176px of content width, and the full name at 15px semibold (~155px) leaves no room beside a 32px icon. The mock uses the short form for the same reason. "Capella" still appears in the browser tab via the unchanged `metadata.title`, and on the login screen.
  - The header moves *inside* `DashboardTabs` (so the sidebar is a sibling of the header, full-height and flush to the viewport's top-left corner, as in the mock) and now renders a view-dependent title: "Cluster Management" / "Lifecycle History". Because the title depends on client tab state, the header can't stay in the server component - `logoutAction` is imported directly into the client component instead, the same way `RefreshButton` already imports `refreshAction`.
  - `app/page.tsx` is reduced to data loading plus a single `<DashboardTabs />` - it renders no chrome of its own.
  - The shell switches from `min-h-screen` (whole page scrolls) to `h-screen` + `overflow-hidden`, with scrolling moved into the content pane. This is the mock's behavior and keeps the nav, brand, and page title pinned while a long table scrolls - appropriate for a dense ops view. The sidebar's nav section gets its own `overflow-y-auto` so a short viewport can't clip the footer controls.
- *Alternative considered*: keep the toggle inside the brand row when expanded (right-aligned) and drop it below when collapsed. Rejected - moving a control between rows based on state is visually unstable for no gain; the toggle keeps its own row directly under the brand block, right-aligned when expanded and centered when collapsed (unchanged behavior from Decision 7).
- *Alternative considered*: keep the full-width header and only add the sidebar brand mark. Rejected - it would show the app name twice and still leave no page title, which is the part of the mock the user was pointing at.

**11. Wordmark restored to the full "Capella Housekeeper" (two-tone); a "Cluster Owners" tile added; the activity chart re-pointed at clusters created; and a daily-spend chart added, derived from month-to-date cost readings. (Fifth revision, direct user request.)**
  - **Wordmark**: reverts Decision 10's short form. "Capella" in `text-ink`, "Housekeeper" in `text-brand`, matching the old header's two-tone treatment. Decision 10 rejected the full name for not fitting at 15px beside the icon; it fits at `text-sm` (14px) with `tracking-tight` and `px-3`/`ml-2.5` instead of `px-4`/`ml-3`, so the sidebar keeps its `w-52` width rather than growing back.
  - **"Cluster Owners" tile**: counts *distinct* `owner` values across the cluster rows, excluding the `"Unknown"` placeholder that `page.tsx` substitutes when no owner could be derived - "Unknown" is the absence of an owner, not a person, and counting it would inflate the number.
  - **"Clusters Created" chart**: replaces Decision 8's "Weekly Activity" (audit-log event counts), now bucketing `clusterRows` by `createdAtMs` per local day. Note this counts clusters that *still exist* - a cluster created and deleted inside the window won't appear, since deleted clusters are removed from the live table (they survive only in history).
  - **"Daily Spend" chart**: the honest version of a cost-per-day chart. Capella's billing endpoint returns **month-to-date** spend (`getBillingUsage` requests the 1st of the month → today), so the stored `actualCost.amountUsd` is a running total, not a daily figure - charting it directly would mislabel a cumulative curve as daily spend. Daily spend is therefore derived as the *increase* in that running total across each day, summed over clusters, in a new pure `dailySpendFromSnapshots()` (`src/lib/costSeries.ts`). Readings come from history snapshots (which carry the full record, including cost) plus each cluster's current record appended at its own `asOf`, since history is only written when a tracked field changes and can lag the live value. Day boundaries are passed in from the client for the same timezone reason as Decision 8.
    - A day yields `null` (rendered `–`), never `0`, when its figure isn't derivable - notably when the day's *start* has no known reading, because a month-to-date total already includes spend from earlier in the month and attributing all of it to its first observed day would overstate that day. A decrease is read as a new billing month, so the day's spend is the new total rather than a negative number.
    - **This environment has no cost data at all**: all 262 stored snapshots have `amountUsd: null` (105 explicitly `no-access` - the configured API key lacks billing permission - and the rest predate the field), which is why the table shows "No billing access". The chart therefore renders an explicit empty state naming that cause, rather than a flat zero line that would read as "$0 spent". The derivation itself is covered by unit tests (`costSeries.test.ts`) rather than by observation, since there is no live data here to observe it against.
- *Alternative considered*: chart the month-to-date total per day (a rising curve) instead of deriving daily deltas. Rejected - it answers "what is the running total" rather than the "costs day by day" that was asked for, though it would have needed no delta arithmetic.
- *Alternative considered*: attribute each cluster's current cost to its creation day. Rejected - that is not a daily spend figure at all, just cost indexed by a different date.

**12. Tiles and charts share one row; the created-clusters chart becomes a peak cluster-count chart reconstructed from history; the brand mark expands the sidebar. (Sixth revision, direct user request.)**
  - **One row**: the two stat tiles and the two charts move from two stacked rows into a single `flex flex-wrap items-stretch` row - tiles size to content, charts take the remaining width (`flex-1 min-w-[280px]`) and wrap only when there isn't room.
  - **"Cluster Count" chart**: replaces Decision 11's "Clusters Created". The metric is now the **peak number of clusters that existed** on each day, counting running *and* turned-off clusters - only deletion ends a cluster's lifetime. That's a different data problem from "created that day": it needs to know about clusters that no longer exist, which the live store doesn't have (deleted clusters are removed from it, per the archived `move-tombstones-to-history` change). History is the only record they existed - and it does carry `deletedAt`, verified against the real store: 5 distinct clusters appear in history, 3 of them deleted with real timestamps, against 2 currently live. `page.tsx` therefore reconstructs a `ClusterLifetime[]` from the latest history snapshot per cluster, then overlays the live records (authoritative for anything still present).
    - The daily figure is the **maximum concurrent** count, not "how many existed at some point that day": if one cluster is deleted in the morning and another created in the afternoon, the peak is 1, not 2. Implemented as a pure, tested `maxClustersPerDay()` (`src/lib/clusterCounts.ts`) that seeds each day with the count alive at its start and sweeps creation/deletion events within the day, tracking the running maximum. Creations are applied before deletions at an identical timestamp so tie ordering can't understate the peak.
  - **Brand mark expands the sidebar**: when collapsed, the mark renders as a button that expands (the chevron below it is easy to miss at rail width). Expanded it reverts to an inert `div` - clicking a brand mark to *collapse* isn't an expectation worth setting, and the chevron already covers that direction.
- *Alternative considered*: count clusters that existed at any point during the day rather than the concurrent peak. Rejected - it double-counts a same-day replacement (delete one, create another) as 2, which misrepresents the fleet size the phrase "how many were available" is asking about.
- *Alternative considered*: derive the count purely from the live table's `createdAtMs`, as the previous chart did. Rejected - it silently omits every deleted cluster, so historical days would be undercounted by exactly the clusters the tool exists to clean up.

**13. The brand mark toggles collapse in both directions; the Action column is treated as an ordinary hideable column, surfacing under "Workflow" when hidden. (Seventh revision, direct user request.)**
  - **Brand mark toggles both ways**: Decision 12 only wired the collapsed state (click to expand). The same button now also collapses when the sidebar is already expanded, matching the dedicated chevron toggle's behavior exactly (`setCollapsed((c) => !c)`), so either control reaches either state. There's no longer an inert-`div` branch for the expanded state.
  - **Action column joins the generic hidden-column mechanism**: `ClusterTable.tsx` already renders any hidden column's cell inside the row-detail panel, grouped by `DETAIL_GROUP_BY_COLUMN_ID`. The Action column (Ask/Turn off/Delete) was hideable via the Columns panel like any other column, but was mapped to the "Cluster" detail group rather than "Workflow" - inconsistent with the Consent column, its closest sibling, which is already mapped to "Workflow". Fixed by changing that one mapping entry; no new rendering path was needed; the existing generic `hiddenFieldsForGroup` renderer (which calls `flexRender` with the cell's own context, so the buttons keep their `meta`/`onResult` wiring) already produces correct output, verified visually with the Action column hidden.
- *Alternative considered*: give the Action column its own bespoke block in the "Workflow" section instead of the generic hidden-column path. Rejected - the generic mechanism already exists specifically so any column behaves identically when hidden; a bespoke block would duplicate it for no behavioral difference.

## Risks / Trade-offs

- **[Risk]** Dropping the table's proportional inset (Decision 6) means very wide screens no longer get any automatic margin around the table beyond the content pane's fixed padding - on an ultra-wide monitor the table could look like it's stretching further than is comfortable to scan. → **Mitigation**: this is what the user explicitly asked for after seeing the alternative; the table's own columns already wrap/constrain content (existing "No horizontal scrolling; cell content wraps" requirement), so extra width mostly reduces wrapping rather than stretching cells arbitrarily thin or wide.
- **[Risk]** Refresh (Decision 9) is no longer reachable from the History view, only from Clusters - a real capability regression versus today (header-mounted Refresh was visible from both views). → **Mitigation**: this is a direct, explicit instruction ("place refresh button to the right from columns button", which only exists in `ClusterTable`); flagged here and in the response to the user rather than silently duplicating the button into `HistoryTable` unasked.
- **[Risk]** Collapsed Slack status loses the inline Reconnect action. → **Mitigation**: the status dot (and its color) remains visible collapsed, so a problem is never silently hidden - reconnecting just requires one click to expand the sidebar first.
- **[Risk]** Switching the shell to `h-screen` + `overflow-hidden` (Decision 10) means the page itself no longer scrolls - only the content pane does. On a very short viewport the sidebar's own column (brand + toggle + nav + footer) could run out of room. → **Mitigation**: the nav section carries `overflow-y-auto` so it scrolls internally before the `mt-auto` footer is pushed off; verified at 900px and at a deliberately short 500px viewport.
- **[Risk]** "Capella" no longer appears anywhere in the dashboard chrome (Decision 10) - only "Housekeeper" beside the brand mark. → **Mitigation**: accepted per the reference screenshots the user supplied, which show exactly that; the full name remains in the browser tab title and on the login page.
- **[Risk]** Always-showing the sidebar (Decision 2) diverges from the mock's responsive behavior, so this isn't a pixel-exact port. → **Mitigation**: proposal.md and this design already scope the change as "styled per the mock," not "identical to," and preserving existing navigation reach takes priority.

## Migration Plan

Single-commit UI change, no data/schema migration. Rollback is a plain revert of `DashboardTabs.tsx` and the corresponding layout adjustment in `app/page.tsx`.
