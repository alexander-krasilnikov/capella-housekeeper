## Context

See proposal.md - Why. Two data-shape facts drive this design:

1. `consentStatus` on a `ClusterRecord` is a **point-in-time** field. A cycle that starts and fully resolves (approved → action performed → reset to `none`) within the trailing 7-day window is invisible if read from the live record - it must be reconstructed from the per-cluster snapshot history (`ClusterSnapshot`, walked in `src/lib/historyView.ts`'s `getLifecycleAuditLog`).
2. `HistoryTrigger` has exactly 8 values (`sync`, `manual-turn-off`, `manual-delete`, `manual-turn-on`, `slack-decision`, `manual-consent-request`, `reconciliation`, `auto-turnoff-decision` - confirmed against `TRIGGER_LABEL`/`TRIGGER_PHRASE` in `historyFields.ts`, which are total maps over the type). Only two of them ever move `consentStatus` into an `approved-*` state: `slack-decision` (owner replied via Slack) and `auto-turnoff-decision` (snooze-limit timeout, system decides and often acts in the same entry). A manual stop/delete (`manual-turn-off`/`manual-delete`) changes `config`/`deletedAt` directly and never touches `consentStatus`/`actionOutcome` at all - it bypasses the consent pipeline entirely rather than resolving a cycle.

## Goals / Non-Goals

**Goals:**
- Reconstruct consent cycles and action attribution entirely from existing audit-log data - no new persisted fields, no change to the consent/reconciliation state machine.
- Share one reconstruction pass between the funnel panel and the actions panel, since both need the same start/approval/execution linkage.

**Non-Goals:**
- Attributing `actionOutcome: failed` or `skipped` - out of scope for this change (the user chose the funnel, actions-by-trigger, and cycle-time directions; the failures-panel idea from exploration was not selected).
- Any change to `ClusterRecord`, `ClusterSnapshot`, or the trigger/state-machine enums.
- Historical backfill correctness guarantees for entries recorded before `workflowNote`/`consentStatusChangedAt` existed - the reconstruction only needs `consentStatus`, `actionOutcome`, and `trigger`, all of which have been recorded since the audit log's inception, so no gap is expected, but this is not separately verified here.

## Decisions

**Cycle reconstruction, not live-field reads.** Walk each cluster's snapshot history in chronological order (reusing the entry shape already produced by `getLifecycleAuditLog`).

A cycle starts at an entry where `consentStatus` transitions *into* `pending` from anything other than `pending` itself - not only from `none`. **Revised after a code-review finding**: the original rule (`from === "none"`) was based on a documentation-invariant that doesn't hold in the real state machine. `notifications.ts`'s `applyConsentNotifications` resets `consentStatus` to `none` and then, if a notification sends, to `pending` within the *same* synchronous mutation, before any history snapshot is written - so the persisted diff on the common age-tier-transition path jumps straight from the prior cycle's terminal status (e.g. `approved-turnoff`) to `pending`, never showing `none`. The snooze-resume path goes `snoozed` → `pending` directly, skipping `none` entirely. A manually re-sent request (`sendManualConsentRequest`) can transition from any prior terminal status too. Recognizing any non-`pending` → `pending` move as a start covers all of these uniformly, without needing to enumerate each path.

It resolves at the next entry where `consentStatus` changes again, classified as:
- **approved** - transitions to `approved-turnoff` or `approved-delete`
- **snoozed** - transitions to `snoozed`
- **expired** - transitions to `expired`
- **cancelled** - transitions to `none` (an age-tier change or a manual turn-off/turn-on reset it, not an owner decision) - discarded, not counted toward any funnel bucket, and critically clears the open-cycle marker so a stale start time can't resurface later as a bogus "still pending" cycle (a second review finding: the original code left the marker set in this case, since `outcomeForResolvedStatus("none")` returns null and nothing else cleared it)
- **pending (unresolved)** - no further `consentStatus` transition found yet

A cycle counts toward the 7-day funnel if its *start* entry's timestamp falls in the trailing window, regardless of where its resolution timestamp falls (addresses point 1 above). Each cycle's `resolvedAtMs` is still reconstructed and retained on the `ConsentCycle` record - it's core reconstruction output - but the funnel summary itself is a plain count per outcome; no duration/median is derived from it (see the "Presentation" decision below - time-to-resolution was built, then explicitly removed per user feedback).

**Action-trigger attribution uses three categories, derived, not read off a single field:**
- **Manual** - any entry with trigger `manual-turn-off` or `manual-delete` (config/deletedAt changed directly; no antecedent approval to trace). Read via the shared `MANUAL_ACTION_TRIGGERS` set (`historyFields.ts`), not an inline comparison.
- **Auto-decided** - an entry where `actionOutcome` transitions to `performed` and that entry's own trigger is `auto-turnoff-decision` (system decided and acted on snooze-limit timeout, typically in one entry).
- **Slack-approved** - an entry where `actionOutcome` transitions to `performed` with trigger `reconciliation`, where the *preceding* entry in the same cycle that set `consentStatus` to `approved-turnoff`/`approved-delete` had trigger `slack-decision` (owner decided via Slack; the reconciliation loop carried it out later).

This requires linking each `actionOutcome: performed` entry back to its cycle's approval entry, which falls out of the same per-cluster chronological walk used for the funnel - no separate lookup. The approval-trigger check itself now reads the shared `APPROVAL_TRIGGERS` set (`historyFields.ts`) rather than re-deriving "which triggers approve a cycle" independently - a code-review finding flagged the original inline logic as free to silently drift from `describeAuditEntry`'s own (already hand-tuned) notion of the same fact.

**Window boundary is an exact rolling 168 hours from now, not calendar-day buckets.** Cycle starts and resolutions are precise timestamps, unlike the existing `maxClustersPerDay`/`dailySpendFromSnapshots` charts which bucket by day for a bar-chart x-axis. Since this feature has no per-day axis (just aggregate counts), day-bucketing would only lose precision at the window edge for no benefit.

**Reconstruction runs over a bounded lookback, not the full audit log since inception.** A code-review finding noted that `reconstructConsentAndActionHistory` scanned every entry for every cluster ever, even though the visible output only covers 7 days - an unbounded cost that grows with the audit log's total history. Fixed by pre-filtering entries to `LINEAGE_LOOKBACK_HOURS` (30 days) before the display window, in `summarizeConsentAndActionHealth`. Exactly 7 days couldn't be used for the pre-filter, since an action performed inside the display window can trace back to an approval that landed just before it (the actions panel intentionally windows by action timestamp, not cycle-start timestamp - see the Impact note on the two panels using different time slices); 30 days is generously larger than any realistic ask-to-execution gap while still bounding cost to a fixed ceiling.

**Computed at render time, same pattern as `clusterCounts.ts`/`costSeries.ts`.** A new module (e.g. `src/lib/consentActionHealth.ts`) takes the full audit log (already assembled server-side for the history tab) and returns the funnel and actions summaries. No new storage, no background job - consistent with how the existing stat-tile row computes its 7-day series on each dashboard render.

**Presentation: horizontal bar chart, one row per panel, folded into the existing stat-tile row.** Per direct user feedback after the first pass shipped (list-style rows in a separate section below the existing tiles): the "Total Clusters" and "Cluster Owners" tiles are both removed outright (the former redundant with three other displays; the latter removed per explicit follow-up feedback), and the funnel/actions panels move into the *same* flex row as the Cluster Count/Daily Spend charts rather than a row of their own. Both panels are now rendered by one shared `BarPanel({title, rows})` component (a code-review finding flagged the original two panel components as near-duplicates) pairing each row's horizontal bar (scaled to that panel's own max, mirroring `DailyBarChart`'s own-max scaling) with its raw count - the bar never replaces the number, since raw counts remain a hard requirement. The funnel panel's per-outcome median time-to-resolution detail, present in the first pass, was likewise removed per explicit follow-up feedback ("consumed time per consent type") - `summarizeFunnel` now returns a plain count per outcome instead of `{ count, medianResolutionMs }`. The actions-taken panel's three categories are labeled plainly "Auto"/"Slack"/"Manual" rather than the longer descriptive labels used internally (`autoDecided`/`slackApproved`/`manual` - see the "Action-trigger attribution" decision above, which is unchanged; only the display labels simplified).

## Risks / Trade-offs

- **[Risk]** Reconstructing cycles requires a full chronological walk per cluster's snapshot history within the lookback window, on every dashboard render. → **Mitigation**: this is the same access pattern (`getLifecycleAuditLog`) already used to render the history tab, now additionally bounded by `LINEAGE_LOOKBACK_HOURS` rather than unbounded total history (see the lookback Decision above); no evidence of remaining cost being a performance concern at current scale.
- **[Risk]** A cluster whose snapshot history was pruned or predates a field (e.g. `consentStatusChangedAt`) could produce an undercounted or misattributed cycle. → **Mitigation**: non-goal, noted above; revisit only if observed in practice.
- **[Risk]** A cycle's approval and its eventual reconciliation-performed execution more than 30 days apart (the lineage lookback bound) would misattribute that action as "Auto-decided" instead of "Slack-approved", since the approval entry falls outside the entries considered. → **Mitigation**: accepted trade-off - a gap that large between owner approval and reconciliation actually executing it would itself indicate a separate operational problem (reconciliation stuck/broken for weeks), at which point an undercounted Slack-approved bar is a minor secondary symptom, not the primary signal an operator would be missing.
- **[Trade-off]** "Slack-approved" vs "Auto-decided" is inferred by tracing trigger lineage rather than being a directly stored fact. This is more logic than a flat count-by-trigger, but is necessary to give the three categories in the proposal their intended meaning (who *decided*, not just which code path executed the API call).
